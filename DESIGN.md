# Cobalt Clarity Web + Admin

## Overview

Cobalt Clarity Web + Admin is a semantic design system for two related product surfaces: public-facing websites and authenticated web applications or admin dashboards. Both surfaces share one visual language, one accessibility model, and one semantic token vocabulary, while allowing different density and layout behavior.

The visual character is calm, professional, highly legible, and operational. Cobalt blue communicates interactive emphasis, slate neutrals create hierarchy, and green, amber, red, and blue are reserved for semantic status and feedback.

The system is organized conceptually in three layers:

1. Foundation values provide the raw visual palette and scales.
2. Semantic tokens describe what a value does, such as `text-primary`, `surface-raised`, `action-primary-background-hover`, or `status-warning-background`.
3. Component tokens map semantic decisions to concrete UI patterns such as buttons, inputs, tables, navigation, status badges, cards, and alerts.

The machine-readable `colors` map is intentionally semantic. Components should reference semantic colors instead of choosing raw hex values directly.

Public websites should generally feel more spacious and editorial. Admin dashboards should generally feel more compact, structured, and information-dense without becoming visually crowded.

## Colors

### Semantic model

Use this naming pattern for colors:

`category-role-property-state`

Not every token requires every segment. Names describe intent rather than appearance.

Examples:

- `text-primary`: the main readable text color.
- `border-subtle`: a low-emphasis divider or boundary.
- `action-primary-background-hover`: hover background for the highest-emphasis action.
- `feedback-danger-foreground`: content communicating an error or failed outcome.
- `status-warning-background`: persistent caution status in dashboard data.
- `navigation-sidebar-item-selected`: selected destination in application navigation.
- `table-row-selected`: selected table row background.

### Background and surface

Background tokens define major canvases. Surface tokens define local containers placed on those canvases.

- `background-primary` is the default page canvas.
- `background-secondary` separates large page regions or dashboard work areas.
- `background-tertiary` is for inset regions and grouped controls.
- `background-inverse` supports dark, high-contrast areas.
- `background-accent` is a light accent-tinted region for highlighted content, selected states, and callouts.
- `background-disabled` is reserved for unavailable controls.
- `background-overlay` appears behind blocking layers such as dialogs.
- `surface-primary` is the default card, menu, dialog, and form surface.
- `surface-secondary` is a quieter alternative surface.
- `surface-raised` is reserved for floating content.
- `surface-sunken` is used for wells, filter regions, grouped controls, and inset areas.

For dashboards, prefer quiet boundaries and tonal surfaces over placing every region inside a separate elevated card.

### Text and icons

Text tokens express hierarchy and semantic meaning, not gray values.

- `text-primary` for headings, labels, and core content.
- `text-secondary` for supporting content.
- `text-tertiary` for metadata and low-emphasis content.
- `text-inverse` for content on dark backgrounds.
- `text-disabled` only for unavailable content or controls.
- `text-accent` for accent-colored labels, highlights, and selected text.
- `text-link` for inline links.
- `text-success`, `text-warning`, `text-danger`, and `text-info` for semantic messaging.

Icons do not have a separate color-token family. SVG icons use `currentColor` and inherit the foreground color of their surrounding text or component.

- An icon next to text inherits that text color by default.
- A standalone neutral icon uses `text-primary`, `text-secondary`, or `text-tertiary` according to its intended emphasis.
- An icon on an inverse surface uses `text-inverse` unless its component defines a more specific foreground token.
- An unavailable icon uses `text-disabled` or inherits the disabled foreground of its component.
- A semantic icon uses `text-success`, `text-warning`, `text-danger`, or `text-info` only when the icon communicates that meaning.
- Icons inside actions, feedback messages, statuses, navigation, and selected elements inherit the corresponding component foreground token instead of selecting a text color independently.

If an icon needs different emphasis from adjacent text, wrap it in an element with the appropriate text token while preserving `currentColor` on the SVG.

### Borders

Borders define controls, tables, grouped regions, and subtle hierarchy.

- `border-primary` is the standard control and visible container border.
- `border-secondary` is a quieter structural border.
- `border-subtle` is used for low-emphasis dividers.
- `border-strong` is for deliberate high-emphasis separation.
- `border-focus` is used for focused controls.
- `border-accent` is the accent-tinted border for highlighted or selected regions.
- Semantic borders belong to validation, feedback, or status UI.
- `table-border` is the default separator within data tables.

Prefer borders over shadows for most dashboard grouping.

### Interactive and action colors

Action tokens describe what the user can do. They answer three questions:

1. What is the action hierarchy? `primary`, `secondary`, `tertiary`, `destructive`, or `link`.
2. What part is styled? `background`, `foreground`, or `border`.
3. What is the state? `default`, `hover`, `active`, or `disabled`.

Primary actions are the strongest call to action in a decision area. Secondary actions are important alternatives. Tertiary actions are low-emphasis utility actions. Destructive actions are reserved for removal, loss, or irreversible consequences. Links handle inline and navigational actions where visited state may be meaningful.

Do not use action colors to communicate system status.

### Feedback versus status

Feedback and status are related but have different purposes.

**Feedback describes what the system is telling the user about an event or result.** Use feedback tokens for alerts, validation, toast messages, save confirmations, errors, warnings, and contextual notices.

- `feedback-success-*`: an operation completed successfully.
- `feedback-warning-*`: an issue may need attention.
- `feedback-danger-*`: an operation failed or input is invalid.
- `feedback-info-*`: neutral contextual information.

**Status describes the persistent state of an entity or workflow.** This distinction is especially important in admin dashboards where status labels appear repeatedly in tables, cards, and detail pages.

Suggested mappings:

- `status-positive-*`: Active, Approved, Completed, Healthy.
- `status-warning-*`: Pending, Paused, At risk, Needs review.
- `status-negative-*`: Failed, Blocked, Rejected, Overdue.
- `status-info-*`: In review, Processing, Scheduled.
- `status-neutral-*`: Draft, Inactive, Archived, Unknown.

Do not automatically map every domain-specific status to green, amber, or red. Preserve meaning consistently across the product and use text labels in addition to color.

### Navigation and selection

Application navigation has its own persistent states. A selected sidebar item represents location, not an action hierarchy and not feedback.

- `navigation-sidebar-background` is the application navigation canvas.
- `navigation-sidebar-item-hover` indicates pointer interaction.
- `navigation-sidebar-item-selected` identifies the current destination.
- `table-row-selected` and `selection-background` indicate selected content.

Do not use `action-primary-background-default` to mark the current navigation destination unless the visual language explicitly calls for the same treatment.

### Data visualization

Charts use a restrained categorical palette. `chart-series-1` through `chart-series-6` provide distinct series colors. `chart-positive` and `chart-negative` are reserved for genuinely positive/negative quantitative meaning such as gain/loss, not arbitrary series assignment.

Use `chart-gridline` and `chart-axis` for quiet structural elements. Do not rely on color alone to distinguish important series; use labels, shapes, direct annotation, line styles, or patterns where necessary.

### Focus

Focus is a global accessibility behavior, not a separate action family. Use `focus-ring` around keyboard-focused interactive elements and `focus-ring-offset` when separation from the underlying surface is required.

A visible focus treatment must not rely only on an internal color change. Preserve focus visibility in tables, menus, tabs, sidebar navigation, compact icon buttons, and dense toolbar controls.

## Typography

Inter is used throughout for neutral, high-legibility interface typography.

Public websites may use larger display and heading styles to create editorial hierarchy. Dashboards should favor compact headings, labels, and data typography so attention remains on tasks and information.

- `display-lg` is reserved for major public-facing statements and should rarely appear in admin dashboards.
- `heading-h1` through `heading-h4` establish page and section hierarchy.
- `body-lg`, `body-md`, `body-sm`, and `body-xs` support different information densities.
- `label-lg`, `label-md`, and `label-sm` are used for controls, navigation, table headers, filters, and badges.
- `caption` is for timestamps, metadata, and supporting annotations.
- `data-lg`, `data-md`, and `data-sm` are for KPI values, totals, measurements, and prominent quantitative data.

Default public website body content uses `body-md`. Default dashboard body and table content may use `body-sm` when the surrounding interface remains readable.

Do not use `body-xs` as a general body style. It is reserved for dense supporting metadata and should not become the default simply to fit more information on screen.

Use tabular numerals in implementation for aligned numeric table columns and metrics when the selected font supports them.

## Layout

The system follows a 4px base rhythm with common increments at 8px, 12px, 16px, 24px, 32px, 48px, and 64px. Use the spacing scale rather than arbitrary values whenever possible.

### Layout modes

The same semantic system supports two density modes:

**Website mode** is spacious and content-led. It uses larger section separation, readable content measures, and generous composition.

**Admin mode** is operational and information-led. It uses smaller gaps, persistent navigation, denser controls, tables, filters, and wider working areas.

Do not make the dashboard feel compact by shrinking text indiscriminately. Density should primarily come from reduced spacing, more efficient grouping, compact controls, and appropriate container widths.

### Page gutters

Website gutters:

- Mobile: `page-gutter-mobile` = 16px
- Tablet: `page-gutter-tablet` = 24px
- Desktop: `page-gutter-desktop` = 32px

Dashboard workspace gutters:

- Mobile: `dashboard-gutter-mobile` = 16px
- Tablet: `dashboard-gutter-tablet` = 20px
- Desktop: `dashboard-gutter-desktop` = 24px

The page shell owns the outer gutter. Individual sections should not add arbitrary horizontal margins to compensate for inconsistent shell spacing.

### Content widths

Choose content width according to the task:

- `content-narrow` = 480px for authentication, focused forms, and narrow task flows.
- `content-readable` = 720px for articles, documentation, long-form guidance, and form-heavy pages.
- `content-standard` = 1200px for general public website and application content.
- `content-dashboard` = 1600px for dashboards, tables, analytics, and data-heavy layouts.

A dashboard may intentionally use the full available workspace beyond `content-dashboard` when the task genuinely benefits from it, particularly large tables or visualizations. Do not stretch prose or form fields just because more width is available.

### Section spacing

Website section spacing:

- Mobile: `section-mobile` = 48px
- Tablet: `section-tablet` = 64px
- Desktop: `section-desktop` = 96px

Admin dashboards do not normally use 96px between operational regions. Prefer 24px to 32px between major dashboard groups and 16px to 24px within panels or work areas.

Use spacing to communicate relationship:

- 4px to 8px: tightly related label, icon, helper text, or metadata.
- 8px to 12px: compact controls and closely related elements.
- 16px to 24px: elements within a content group or card.
- 24px to 32px: distinct dashboard groups.
- 48px to 64px: major content separation.
- 96px: generous public website section separation on large screens.

### Dashboard shell

The standard desktop application shell uses:

- Expanded sidebar: `sidebar-expanded` = 256px.
- Collapsed sidebar: `sidebar-collapsed` = 72px.
- Top bar: `topbar-height` = 64px.
- Main workspace: fluid, using dashboard gutters and an optional `content-dashboard` maximum width.

The sidebar should remain visually stable across application screens. Do not change its width or navigation spacing per page.

On smaller screens, convert the persistent sidebar to an off-canvas or temporary navigation pattern. Do not squeeze a desktop sidebar and main workspace side by side on narrow viewports.

### Grid and composition

For dashboards, use CSS Grid or Flexbox with consistent tokenized gaps. A 12-column desktop grid is a useful conceptual reference for complex workspaces, but components should respond to available width rather than depending on rigid device classes.

KPI cards may form 2–4 columns depending on available width. Data tables and primary analysis surfaces should receive width before secondary panels. Side-by-side panels should stack when either panel would become difficult to scan or operate.

Avoid absolute positioning for primary page structure.

### Density and control sizing

Control heights are semantic size references:

- `control-height-sm` = 32px for compact desktop dashboard controls.
- `control-height-md` = 40px for standard dashboard controls.
- `control-height-lg` = 44px for public website controls, prominent actions, and touch-friendly use.
- `touch-target-min` = 44px is the minimum intended touch target reference.

A 32px visual control may be appropriate in a pointer-driven desktop dashboard, but compact controls must not create inaccessible touch interactions. On touch-oriented layouts, increase the interactive target to at least the touch-target reference.

Use compact density selectively for tables, filter bars, toolbars, and repeated utility controls. Primary forms and consequential actions should remain comfortable.

### Tables and horizontal overflow

Data tables should prioritize scanability and alignment.

- Keep headers concise and visually distinct.
- Align text columns left and numeric columns right where appropriate.
- Keep row actions predictable, usually at the end of the row.
- Use `table-row-hover` only for rows with meaningful hover affordance or scanning assistance.
- Use `table-row-selected` only for actual selection.
- Preserve visible keyboard focus for interactive cells and row actions.

On narrow screens, do not force every desktop table into a compressed unreadable grid. Choose an appropriate responsive strategy: horizontal scrolling inside a contained table region, column prioritization, stacked records, or a dedicated mobile detail pattern.

### Full-width sections

Public website backgrounds and decorative treatments may extend to viewport edges while their content remains aligned to the page container.

In dashboards, persistent shell regions such as the sidebar and top bar may be full-height or full-width, while the working content follows dashboard gutters.

## Elevation & Depth

Depth should remain subtle. Prefer tonal differences and borders before adding shadows.

Recommended hierarchy:

1. Page or workspace background: `background-primary` or `background-secondary`.
2. Standard container: `surface-primary` with a quiet border.
3. Raised menu, dropdown, or popover: `surface-raised` with restrained shadow.
4. Modal or blocking layer: `surface-raised` above `background-overlay`.

Dashboards often contain many adjacent regions; excessive card shadows create visual noise. Use borders and background changes for structure and reserve elevation for elements that actually float above the workspace.

Sticky top bars and table headers may use a subtle border or very light shadow only when needed to preserve separation during scrolling.

## Shapes

The shape language is moderately rounded and practical.

- `rounded.md` (8px) is the default for buttons, inputs, tabs, and compact controls.
- `rounded.lg` (12px) is the default for public website cards and larger grouped containers.
- Dashboard cards may use `rounded.md` or `rounded.lg` depending on density.
- `rounded.xl` (16px) is reserved for larger feature surfaces or dialogs.
- `rounded.full` is reserved for pills, status badges, avatars, and circular controls.

Do not use many unrelated radius values on the same screen. Dense data tables usually rely on the outer container radius rather than rounding individual rows or cells.

## Components

### Buttons

Primary, secondary, tertiary, and destructive buttons preserve the same action hierarchy across websites and dashboards.

Use the standard 44px button for public-facing pages, forms, primary flows, and touch-friendly contexts. Compact 32px controls may be used in dense desktop toolbars and repeated dashboard utilities, but should not replace comfortable controls everywhere.

Prefer one dominant primary action per major decision area. A dashboard page may contain multiple localized primary actions when they belong to clearly separate panels or workflows, but avoid creating a field of equally dominant blue buttons.

Button icons use `currentColor` and inherit the button's action foreground token in every state. Icon-only buttons follow the same variant and state colors as buttons with visible labels; they do not introduce a separate icon color.

### Inputs, search, and filters

Inputs use `surface-primary`, `text-primary`, and `border-primary`. Focus changes the border to `border-focus` and adds the global focus ring. Disabled inputs use the disabled semantic tokens.

Standard forms should use comfortable controls. Compact inputs are appropriate for dashboard filter bars, table filters, and dense search/filter interfaces.

Search fields may use `surface-secondary` to distinguish utility search from data-entry forms.

Validation states use feedback semantics and include text or icon cues. Do not communicate validation by border color alone.

### Sidebar navigation

The sidebar uses a dark inverse canvas to clearly separate global application navigation from the workspace.

- Default items use muted inverse foreground.
- Hover reveals a subtle dark surface and stronger foreground.
- Selected items use `navigation-sidebar-item-selected` and a high-contrast foreground.
- Selected state represents the current location, not a primary action.
- Sidebar icons and labels should align consistently.
- Collapsed navigation must retain accessible labels through tooltips or another clear mechanism.

Do not use status, feedback, or destructive colors for normal navigation emphasis.

### Top bar

The top bar provides global utilities such as search, organization/account context, notifications, help, and user profile controls.

Keep it visually quieter than the primary page content. Use a bottom border for separation before adding shadow.

### Tabs

Tabs represent peer views of the same context. They are not a replacement for global navigation.

- Default tabs use secondary text.
- Hover may use a subtle tertiary action surface.
- Selected tabs use accent emphasis and must remain identifiable without relying solely on color; an underline, indicator, or selected surface should be present in implementation.

### Cards and statistic cards

Public website cards may use 24px padding and more generous radius. Dashboard cards should often use 16px padding to improve information density.

Statistic cards should emphasize the value first, then label, comparison, timeframe, or contextual metadata. Use `data-*` typography for important quantitative values. Do not make every metric card visually loud; reserve semantic colors for meaningful status or change.

### Tables

Tables are first-class dashboard components, not collections of decorative cards.

Use `table-header-background`, `table-row-background`, `table-row-hover`, `table-row-selected`, and `table-border` consistently.

Keep row height sufficient for scanability and interactions. Use compact density for large datasets, but avoid shrinking labels below readable levels. Sorting, filtering, selection, pagination, and row actions require visible focus and clear interactive affordances.

The current DESIGN.md component token model does not need to encode every table border or column rule. Document structural behavior in prose and use the semantic border tokens in implementation.

### Status badges

Status badges communicate persistent entity or workflow state, not transient feedback.

Use:

- `badge-positive` for stable positive states such as Active or Approved.
- `badge-warning` for caution states such as Pending or At risk.
- `badge-negative` for problematic states such as Failed or Blocked.
- `badge-info` for process states such as In review or Processing.
- `badge-neutral` for Draft, Inactive, Archived, or unknown states.

Always include a text label. Do not display a colored dot alone when the meaning is important.

### Alerts and feedback

Alerts use the feedback family because they communicate system messages, events, or results.

Examples:

- "Changes saved" uses feedback success.
- "Your session expires in 5 minutes" uses feedback warning.
- "The report could not be generated" uses feedback danger.
- "Data refreshes every 30 minutes" uses feedback info.

A persistent `Active` badge should use status-positive, not feedback-success.

### Dropdowns, menus, and modals

Dropdowns and menus use raised surfaces and should be visually attached to the control that opened them. Keep shadows restrained and preserve clear hover, selected, and keyboard focus states.

Modals are reserved for focused decisions or tasks that should interrupt the current workflow. Do not put routine dashboard navigation or large multi-step work areas inside modals when a page or side panel would provide better context.

### Charts

Charts should inherit surrounding typography and use the chart semantic palette.

- Keep gridlines quiet.
- Label important values directly when possible.
- Use consistent series-color assignment within the same analytical context.
- Do not assign positive/negative colors merely for variety.
- Provide text summaries or accessible alternatives for essential chart information.
- Avoid 3D effects, decorative gradients, and unnecessary chart chrome.

## Do's and Don'ts

- Do name tokens by purpose: `text-secondary`, not `gray-600`.
- Do keep action hierarchy separate from interaction state.
- Do keep action, feedback, status, navigation, and selection semantics distinct.
- Do use status tokens for persistent workflow/entity states and feedback tokens for messages or outcomes.
- Do use `primary`, `secondary`, and `tertiary` to express action emphasis.
- Do reserve `destructive` for actions involving removal, loss, or irreversible consequences.
- Do use a global focus ring consistently across buttons, links, inputs, table controls, navigation, tabs, menus, and filters.
- Do maintain WCAG AA contrast for normal text and essential interactive content.
- Do implement SVG icons with `currentColor` and set color on their surrounding text or component.
- Do pair semantic color with labels, icons, position, or other non-color cues when meaning matters.
- Do use spacing tokens for component padding and semantic control-height tokens for control sizing.
- Do make public website layouts more spacious and dashboard layouts more operationally dense without creating two unrelated visual systems.
- Do give tables, filters, navigation, and status patterns first-class design rules in admin experiences.
- Do prefer borders and tonal surfaces before shadows in dense dashboards.
- Do keep numeric data aligned and easy to scan.
- Do preserve comfortable touch targets when dashboard layouts are used on touch devices.
- Don't create hover or active tokens solely for symmetry when the design has no state change.
- Don't reference raw hex colors from component implementation when a semantic token exists.
- Don't assign an independent color to an icon when it should inherit its component foreground.
- Don't use `text-disabled` as a general-purpose muted text color.
- Don't use danger red as a decorative accent.
- Don't use feedback colors as arbitrary dashboard category colors.
- Don't use a success alert style as the default representation of an Active status; use status semantics.
- Don't make every dashboard region a floating card.
- Don't shrink body text merely to fit more data.
- Don't force desktop tables into unreadably narrow mobile columns.
- Don't hide row actions exclusively behind hover when keyboard or touch users also need them.
- Don't remove visible focus outlines unless an equally visible replacement is provided.
- Don't let multiple primary actions compete in the same decision area without a clear reason.
